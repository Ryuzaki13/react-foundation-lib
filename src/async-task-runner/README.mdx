# Последовательный async runner и абсолютный deadline

Публичный импорт: `@ryuzaki13/react-foundation-lib/async-task-runner`.
Runner объединяет повторные сигналы, повторяет отказавшую задачу и корректно
завершает lifecycle. Он не знает о HTTP, БД, React или предметном составе.
Создание и импорт не вызывают `run` и не создают таймеры.

`createDeadlineTimer` дополняет runner независимым одноразовым пробуждением в
абсолютный момент. Он не задаёт polling или retry policy и не вызывает
предметную работу при промежуточных частях длинного ожидания.

```ts
import { createCoalescingTaskRunner } from "@ryuzaki13/react-foundation-lib/async-task-runner";

const runner = createCoalescingTaskRunner({
	run: synchronizeCurrentState,
	onError: reportTaskFailure,
	retryDelayMs: 5000
});
await runner.start();
// Внешний lifecycle явно запускает и завершает ресурс.
await runner.stop();
```

`retryDelayMs` обязателен. `pollIntervalMs` необязателен и не имеет default:
периодичность, допустимую задержку синхронизации и нагрузку выбирает приложение.
Обе задержки должны быть целыми числами от 1 до 2147483647 ms включительно;
некорректная настройка даёт `RangeError` при создании, до любых побочных эффектов.

## Допуск и объединение сигналов

`start(): Promise<void>` создаёт поколение и первую попытку. Повторный start
идемпотентен: присоединяется к текущей попытке, если она выполняется, либо
возвращает fulfilled promise без нового прохода. Это допуск lifecycle, а не
проверка readiness или подтверждение актуальности данных во время retry.

`wake(): Promise<void>` не запускает неактивный runner. В активном поколении он
запускает попытку либо возвращает promise уже выполняющейся попытки и запрашивает
ровно один следующий проход. Любое число таких сигналов не создаёт очередь.
Следующий проход выполняется отдельной timer-задачей после завершения текущего.

Promise start/wake относится **текущей попытке**, включая её обработчик ошибки,
но не подтверждает завершение объединённого будущего хвоста. Если stop отозвал
поколение до первой microtask, callback ещё не начавшейся попытки не выполняется.
Для гарантии завершения всего уже допущенного выполнения используется stop.

Явный wake отменяет запланированную задержку retry и немедленно допускает новую
попытку, если текущая уже завершилась. Poll этого не делает и не обходит backoff.
Сигналы во время отказавшей попытки не заменяют delayed retry немедленным хвостом.
Повторный start также не ускоряет retry.

## Отказы задачи и reporter

При отказе run обработчик `onError(error): void | Promise<void>` вызывается один
раз и ожидается, после чего планируется один delayed retry. Promise текущей
попытки отклоняется исходной task error. Запланированные фоновые вызовы имеют
внутренний rejection boundary: они не создают unhandled rejection.
Reporter отвечает за безопасную диагностику; библиотека ничего не логирует.

Если onError сам бросил исключение либо отклонил promise, точная reporter error
сохраняется, таймеры и хвост удаляются, автоматические повторы прекращаются.
Следующие start/wake отклоняются reporter error; stop ожидает текущую попытку
и тоже отклоняется этой ошибкой. Значения `undefined` и `null` не теряются.
Текущая попытка по-прежнему отклоняется исходной task error, не подменяя её.
Восстановление требует явного stop/drain, обработки его отказа и нового start.

## Остановка и повторный запуск

`stop(): Promise<void>` сразу закрывает поколение, удаляет таймеры и накопленный
хвост, затем ждёт уже выполняющиеся run/onError. Обычная task error уже передана
onError и caller текущей попытки: stop не повторяет её как собственный отказ.
Отказ admitted задачи обрабатывается и после начала stop, но не заводит таймер.

Stop не имитирует отмену атомарной операции: уже начатая задача может завершиться
успешно, в том числе выполнить COMMIT, прежде чем завершится drain. Повторные
stop разделяют тот же drain promise. Start во время drain ждёт его; более поздний
stop отменяет такой отложенный start, не позволяя старому запросу оживить ресурс.

Нельзя ожидать собственные start, wake или stop внутри run/onError: start/wake
возвращают promise текущей попытки, а stop ждёт этот callback. Такое ожидание
создаёт цикл самодренирования. Остановка принадлежит внешнему lifecycle.
Callback, который никогда не завершается, удерживает drain; timeout и реальная
отмена внешней операции остаются ответственностью приложения.

## Абсолютный одноразовый срок

```ts
import { createDeadlineTimer } from "@ryuzaki13/react-foundation-lib/async-task-runner";

const deadline = createDeadlineTimer({
	onDue: () => {
		// Async callback имеет собственную обработку отказа у владельца работы.
		void runner.wake().catch(reportTaskFailure);
	}
});
deadline.schedule(nextEffectiveAtMs);
// При остановке сначала отменяется допуск timer, затем ожидается работа runner.
deadline.cancel();
await runner.stop();
```

Создание timer не запускает callback и не создаёт native timer.
`schedule(deadlineAtMs: number | null): void` заменяет прежний срок, а `null`
отменяет его. Срок — безопасное целое число абсолютных Unix milliseconds;
`NaN`, бесконечность, дробное или небезопасное число дают `RangeError` до
побочных эффектов и не отменяют уже назначенный корректный срок. Повтор того
же pending срока идемпотентен. Просроченный срок, включая отрицательное число,
выполняется отдельной timer-задачей, а не синхронно внутри `schedule`.

Задержка каждого native timer не превышает 2147483647 ms. Если абсолютный срок
дальше, ожидание разбивается на части с повторной проверкой `Date.now()`.
Промежуточные части не вызывают `onDue`, не читают внешние источники и не
выполняют фоновые предметные проходы. Одновременно существует не более одного
native timer. В Node используется `unref`: само ожидание не удерживает процесс.

`onDue` вызывается один раз за назначенный срок. До вызова срок снимается, поэтому
callback может назначить следующий срок. `cancel(): void` удаляет pending timer
и отзывает его поколение; поздние callbacks отменённого или заменённого срока
игнорируются. Cancel не отменяет уже начавшуюся работу внутри `onDue`. Новая
`schedule` после cancel разрешена; окончательный lifecycle принадлежит caller.

Timer не знает timezone, календарных правил, БД, SQL, transport или React.
Вычисление абсолютного срока, обработка синхронных ошибок и async rejection
в callback, retry и остановка атомарной работы остаются у caller. Он не ожидает
Promise, возвращённый callback, и не добавляет собственной диагностики.

Точность зависит от event loop и системных часов. После перевода часов назад
ранний callback перевзводит оставшееся ожидание; после перевода часов вперёд
просроченность обнаруживается при ближайшем уже назначенном timer callback,
не через скрытый interval. Этот primitive не гарантирует немедленную реакцию
на изменение часов и не заменяет внешний startup/reconnect catch-up.
