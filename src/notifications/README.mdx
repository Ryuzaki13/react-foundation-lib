# Notifications

Модуль `@ryuzaki13/react-foundation-lib/notifications` хранит активный toast-стек и историю сохраняемых уведомлений, а также предоставляет два способа управления ими:

- Zustand-store — для React-интерфейса, который отображает уведомления;
- объект `notify` — для императивных вызовов из обработчиков, сервисов и `try/catch`.

Модуль **не рисует интерфейс**. Компонент toast/snackbar создаёт приложение: он подписывается на `store`, отображает `items` и вызывает действия уведомления.

## Когда использовать

Подходит для сообщений вроде:

- «Изменения сохранены»;
- «Не удалось загрузить данные»;
- «Файл формируется…» с последующей заменой на результат;
- предупреждения с одной или несколькими кнопками-действиями.

Для ошибок внутри формы лучше показывать сообщение рядом с полем. Уведомление — дополнительный, а не единственный канал обратной связи.

## Импорт

Модулю нужен peer dependency `zustand`.

```bash
npm install zustand
```

```ts
import { bindNotifications, createNotificationsStore, notify, type Notification } from "@ryuzaki13/react-foundation-lib/notifications";
```

Используйте только публичный subpath `/notifications`. Импорт внутренних файлов пакета не является публичным контрактом.

## Быстрый старт

### 1. Создайте один store приложения

```ts
// notificationsStore.ts
import { bindNotifications, createNotificationsStore } from "@ryuzaki13/react-foundation-lib/notifications";

export const notificationsStore = createNotificationsStore();
export const unbindNotifications = bindNotifications(notificationsStore);
```

`createNotificationsStore()` возвращает vanilla Zustand-store. Его следует создать вне React-компонента, иначе каждый рендер может создать новую независимую очередь.

`bindNotifications(store)` связывает глобальный фасад `notify` с этим store. Без привязки вызов `notify.success(...)` выбросит ошибку.

### 2. Подпишите UI на store

```tsx
import { useStore } from "zustand";

import { notificationsStore } from "./notificationsStore";

export function NotificationsViewport() {
	const items = useStore(notificationsStore, (state) => state.items);
	const dismiss = useStore(notificationsStore, (state) => state.actions.dismiss);

	return (
		<section aria-label="Уведомления" aria-live="polite">
			{items.map((item) => (
				<article key={item.id} role={item.type === "error" ? "alert" : "status"}>
					{item.title && <strong>{item.title}</strong>}
					<p>{item.message}</p>

					{item.actions?.map((action) => (
						<button key={action.label} type="button" onClick={action.onClick}>
							{action.label}
						</button>
					))}

					{item.dismissible !== false && (
						<button type="button" onClick={() => dismiss(item.id)}>
							Закрыть
						</button>
					)}
				</article>
			))}
		</section>
	);
}
```

`items` содержит только активные toast-уведомления и ограничен шестью элементами. Для отдельного центра уведомлений, страницы или содержимого диалога подписывайтесь на `state.history`: эта коллекция не сокращается при TTL, ручном закрытии и переполнении toast-стека. По умолчанию все уведомления сохраняются; явный `retainInHistory: false` оставляет уведомление только в активном стеке.

### 3. Показывайте уведомления

```ts
notify.success("Данные сохранены");
notify.info("Началась синхронизация", { title: "Синхронизация" });
notify.warning("Соединение нестабильно", { ttlMs: 0 });
notify.error("Не удалось сохранить запись", { ttlMs: 15_000 });
```

Значение `ttlMs: 0` или отрицательное число отключает автоматическое закрытие.

## Модель уведомления

```ts
type NotificationType = "error" | "warning" | "info" | "success";
type NotificationTone = "neutral" | NotificationType;
type NotificationId = string;

type NotificationAction = {
	label: string;
	onClick: () => void | Promise<void>;
	tone?: NotificationTone;
};

type Notification = {
	id: NotificationId;
	type: NotificationType;
	title?: string;
	message: string;
	createdAt: number;
	ttlMs?: number;
	dismissible?: boolean;
	actions?: NotificationAction[];
	retainInHistory?: boolean;
};
```

`createdAt` — Unix-время в миллисекундах. `dismissible: false` означает, что UI не должен показывать обычную кнопку закрытия. Это только договор с UI: store не запрещает программный `dismiss(id)`.

`actions` содержат функции и потому не сериализуются. Не сохраняйте очередь уведомлений в JSON, localStorage или серверной базе.

`retainInHistory: false` запрещает хранить уведомление в `history`. Поле необязательно: его отсутствие сохраняет прежнее поведение и прежнюю форму объекта уведомления. `true` явно разрешает сохранение. Политика действует только на историю этого store, а не на сетевой транспорт, внешние журналы или другие хранилища.

## API store

### `createNotificationsStore()`

Создаёт независимый store со структурой:

```ts
type NotificationsStore = {
	items: Notification[];
	history: Notification[];
	actions: {
		push(input): NotificationId;
		update(id, patch): boolean;
		upsert(inputWithId): NotificationId;
		dismiss(id): void;
		clear(): void;
		clearHistory(): void;
	};
};
```

`items` — стек видимых toast-уведомлений, ограниченный шестью элементами. `history` — история сохраняемых уведомлений за время жизни store. Новое уведомление помещается в начало стека, а в историю — только если не задан `retainInHistory: false`. При добавлении с уже существующим `id` старый элемент заменяется, а новый получает новое `createdAt` и политику нового `push`; отказ от истории удаляет и прежнюю запись с этим ID.

История живёт в памяти и не является журналом аудита: она сбрасывается при пересоздании store или явном `clearHistory()`. Поскольку `actions` уведомлений содержат функции, модуль намеренно не сохраняет историю в `localStorage` и не сериализует её.

### `push(input)`

Добавляет уведомление и возвращает его `id`.

```ts
const id = notificationsStore.getState().actions.push({
	type: "warning",
	title: "Проверка",
	message: "Некоторые поля не заполнены",
	ttlMs: 8_000,
	dismissible: true
});
```

Если `id` не передан, он генерируется из текущего времени и случайной части. Это идентификатор UI, а не криптографический или бизнес-идентификатор.

Если `ttlMs` отсутствует, внутренний таймер всё равно запускается на 10 секунд. При этом в объекте уведомления поле остаётся `undefined`.

### Эфемерный toast без истории

Если текст нужен только во время краткого показа и не должен оставаться в общем центре уведомлений, задайте политику при добавлении:

```ts
const id = notificationsStore.getState().actions.push({
	type: "info",
	message: "Краткое уведомление",
	retainInHistory: false
});

// Обновление без новой политики сохраняет отказ от истории.
notificationsStore.getState().actions.update(id, { message: "Обновлённое краткое уведомление" });
```

Видимость, действия и TTL работают как у обычного toast. Закрытие, истечение TTL и вытеснение из стека не добавляют его текст в историю. Отдельного реестра закрытых эфемерных уведомлений нет: после закрытия новый `push` или отсутствующий `upsert` с тем же ID создаёт новое уведомление с новой политикой.

### `update(id, patch)`

Частично меняет существующий элемент. Возвращает `true`, если элемент найден, иначе `false`.

```ts
const updated = notificationsStore.getState().actions.update(id, {
	type: "success",
	message: "Проверка завершена",
	ttlMs: 2_500
});
```

`id` и `createdAt` изменить нельзя. Таймер перестраивается только тогда, когда в patch явно присутствует ключ `ttlMs`. Изменение одного `message` не продлевает исходный срок жизни.

Если `retainInHistory` отсутствует или равен `undefined`, сохраняется текущая политика. Явный `false` удаляет из истории запись этого ID, не затрагивая остальные уведомления. Явный `true` возвращает активное уведомление в начало истории, если его там нет; существующая запись обновляется на прежнем месте без дубликата.

После `clearHistory()` обычное обновление не возвращает текст в историю, даже если у активного уведомления сохранился `retainInHistory: true`. Для возврата нужно снова явно передать `true` в patch. Если активного уведомления уже нет, `update` возвращает `false` и не создаёт запись истории.

### `upsert(input)`

Обновляет элемент с заданным `id`, а если его нет — добавляет новый.

```ts
notificationsStore.getState().actions.upsert({
	id: "import-users",
	type: "info",
	message: "Импортировано 40 из 100 строк",
	dismissible: false
});
```

Важная деталь: при обновлении существующего элемента `upsert` меняет `type`, `title`, `message`, `ttlMs` и `dismissible`, но не заменяет `actions`. Для явной смены действий используйте `update(id, { actions })`. Поле `retainInHistory` следует правилам `update`: отсутствие или `undefined` сохраняет прежнюю политику, определённое значение меняет её явно. Если toast отсутствует, применяется обычный `push` с переданными параметрами.

### `dismiss(id)`, `clear()` и `clearHistory()`

`dismiss(id)` скрывает один toast и очищает его таймер. `clear()` скрывает весь toast-стек и очищает все таймеры. Обе операции сохраняют существующие записи в `history` и не добавляют туда уведомления с отказом от истории.

`clearHistory()` явно очищает историю, не закрывая активные toast-уведомления. Чтобы полностью сбросить обе коллекции, последовательно вызовите `clear()` и `clearHistory()`.

## Императивный API `notify`

### Привязка и жизненный цикл

```ts
const unbind = bindNotifications(notificationsStore);

// При полном демонтаже приложения:
unbind();
```

Одновременно фасад хранит только одну привязку. Повторный `bindNotifications(otherStore)` переключит вызовы на другой store. Старый cleanup не отвяжет новый store.

Пакет не экспортирует `NotificationsProvider`, несмотря на текст ошибки при отсутствии привязки. Provider или другой lifecycle-компонент является ответственностью приложения.

### Основные методы

```ts
notify.push(input);
notify.upsert(inputWithId);
notify.update(id, patch);
notify.dismiss(id);
notify.clear();
notify.clearHistory();

notify.success(message, options);
notify.info(message, options);
notify.warning(message, options);
notify.error(message, options);
```

Сокращённые методы автоматически подставляют `type`, но принимают остальные параметры `push`, включая `id`, `title`, `ttlMs`, `dismissible`, `actions` и `retainInHistory`.

### Долгая операция: `notify.progress()`

```ts
async function importFile(file: File) {
	const progress = notify.progress("Читаем файл…", {
		id: "users-import",
		title: "Импорт пользователей"
	});

	try {
		progress.update("Отправляем данные…");
		await upload(file);
		progress.success("Импорт завершён");
	} catch (error) {
		progress.error("Импорт завершился с ошибкой");
		throw error;
	}
}
```

Начальное уведомление имеет `type: "info"` и `dismissible: false`. Возвращаемый объект содержит:

- `id` — идентификатор уведомления;
- `update(message)` — меняет текст, не перезапуская таймер;
- `success(message, ttlMs = 2500)` — делает уведомление успешным и закрываемым;
- `error(message, ttlMs = 5000)` — делает уведомление ошибкой и закрываемым;
- `dismiss()` — скрывает toast, сохраняя уведомление в истории.

При переданном стабильном `id` повторный `progress` продолжит существующий элемент. Это удобно для операции, которая может стартовать из нескольких мест.

## Browser и SSR

Store использует `window.setTimeout` и `window.clearTimeout`. Создать store можно заранее, но методы, которые запускают или очищают таймеры, предназначены для браузера. Не вызывайте `push`, `update` с `ttlMs`, `dismiss` или `clear` во время серверного рендера.

Практически безопасная схема: создавать и привязывать store в client entrypoint либо в модуле, который импортируется только браузерным приложением.

## Доступность интерфейса

Store не задаёт ARIA-разметку. В UI рекомендуется:

- использовать `aria-live="polite"` для обычных сообщений;
- использовать `role="alert"` только для действительно срочных ошибок;
- давать кнопке закрытия понятное доступное имя;
- не делать TTL слишком коротким, если уведомление содержит много текста или действия;
- обеспечить управление действиями с клавиатуры.

## Частые ошибки

### Вызов `notify` до `bindNotifications`

```ts
// Ошибка времени выполнения: store ещё не привязан.
notify.success("Готово");
```

Сначала создайте store и выполните `bindNotifications` в точке запуска приложения.

### Создание store внутри тела компонента

```tsx
function App() {
	// Плохо: при повторном рендере можно потерять очередь и таймеры.
	const store = createNotificationsStore();
	return null;
}
```

Создайте singleton на уровне модуля или один раз через подходящий lifecycle-контейнер.

### Ожидание, что `dismissible: false` блокирует удаление

Это только поле модели для UI. `notify.dismiss(id)` всё равно удалит элемент.

### Использование уведомления вместо состояния операции

История живёт в памяти страницы. Не используйте её как журнал аудита, источник истины о фоновой задаче или долговременное хранилище ошибок.

## Краткая карта API

| Экспорт                      | Назначение                                               |
| ---------------------------- | -------------------------------------------------------- |
| `createNotificationsStore()` | Создать независимый Zustand-store toast-стека и истории  |
| `bindNotifications(store)`   | Привязать store к глобальному фасаду `notify`            |
| `notify`                     | Императивно добавлять, обновлять и закрывать уведомления |
| `Notification`               | Полная модель сохранённого элемента                      |
| `NotificationPushInput`      | Параметры добавления элемента                            |
| `NotificationUpdatePatch`    | Допустимые поля частичного обновления                    |
| `NotificationsState`         | Активные `items` и история сохраняемых уведомлений       |
| `NotificationsActions`       | Действия toast-стека и явная очистка истории             |
| `NotificationsStoreApi`      | Тип vanilla Zustand-store                                |
| `NotificationAction`         | Кнопка-действие уведомления                              |
