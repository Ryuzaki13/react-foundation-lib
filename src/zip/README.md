# Упаковка файлов в ZIP

Публичный импорт: `@ryuzaki13/react-foundation-lib/zip`.

`createZipBlob` принимает готовые `{ blob, filename }` и возвращает
`Promise<Blob>` с MIME `application/zip`. Модуль не выполняет сетевые запросы,
не скачивает результат, не зависит от React и не содержит предметных правил.
Импорт не создаёт worker, таймеры или DOM-элементы.

## Подключение

```sh
pnpm add @ryuzaki13/react-foundation-lib fflate
```

Для `/zip` нужна явно установленная optional peer dependency
`fflate >=0.8.3 <0.9.0`. Наличие транзитивной зависимости у `write-excel-file`
не заменяет её объявления в host-проекте. `fflate` остаётся внешней зависимостью
сборки Foundation; совместимые потребители могут использовать одну версию.

```ts
import { downloadFileFromBlob } from "@ryuzaki13/react-foundation-lib/dom";
import { createZipBlob } from "@ryuzaki13/react-foundation-lib/zip";

const archive = await createZipBlob([
	{ blob: new Blob(["Первый документ"]), filename: "Документ.txt" },
	{ blob: new Blob(["id,title\n1,Пример"]), filename: "Таблица.csv" }
]);

// Скачивание принадлежит браузерному сценарию и выполняется по действию пользователя.
downloadFileFromBlob("Документы.zip", archive);
```

Готовый архив также можно передать в `FormData`, сохранить или показать
в собственном сценарии. Имя самого архива выбирает вызывающая сторона.

## Публичный контракт

```ts
export type ZipFile = {
	readonly blob: Blob;
	readonly filename: string;
};

export type CreateZipBlobOptions = {
	readonly compression?: "store" | "deflate";
	readonly signal?: AbortSignal;
};

export declare function createZipBlob(files: readonly ZipFile[], options?: CreateZipBlobOptions): Promise<Blob>;
```

`File` является `Blob` и принимается в поле `blob`. Поле `filename` всегда
обязательно: именно оно определяет имя записи, независимо от `File.name`.
Состав и имена фиксируются до первого асинхронного чтения; исходные Blob
не изменяются. Порядок записей соответствует порядку входного массива.

Пустой массив создаёт корректный пустой ZIP. Пустой Blob сохраняется как файл
нулевого размера. MIME исходных Blob и `File.lastModified` не переносятся:
используется обычная запись ZIP с текущим временем создания.

## Сжатие

| Режим                 | Поведение                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `store`, по умолчанию | Упаковка без сжатия. Подходит для PDF, изображений, XLSX и других уже сжатых файлов. Worker не создаётся.                   |
| `deflate`             | Нативное потоковое сжатие. Полезно для текста, CSV, JSON и другого хорошо сжимаемого содержимого. Уровень выбирает браузер. |

```ts
const archive = await createZipBlob(files, { compression: "deflate" });
```

Режим применяется ко всем записям. Автоматического определения по расширению,
распаковки, шифрования и пароля нет. Для `deflate` необходим нативный
`CompressionStream` с поддержкой формата `deflate-raw`. При отсутствии API или
поддержки формата Promise отклоняется с `TypeError` до чтения первого файла;
`store` остаётся доступным. Для пустого архива компрессор не требуется.
Подробности: [CompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/CompressionStream/CompressionStream).

Оба режима работают без Web Workers и не требуют `worker-src blob:` в CSP.
Применение native stream устраняет зависимость от загрузки Blob Worker:
асинхронный API `fflate` может не передать её отказ из-за CSP вызывающему коду.
Скрытого fallback к другому компрессору нет.

## Имена и ошибки

Все имена проверяются до чтения первого Blob. Кириллица, emoji и пробелы
сохраняются без переименования и Unicode-нормализации.

`TypeError` отклоняет:

- пустое или состоящее только из пробельных символов имя;
- `.` и `..`, разделители `/` и `\`, двоеточие;
- управляющие символы U+0000–U+001F, U+007F–U+009F и непарные UTF-16 суррогаты;
- точное повторение имени;
- неизвестный режим сжатия, переданный из нетипизированного кода.

Каталоги не поддерживаются: каждая запись находится в корне ZIP. Дубликаты
сравниваются с учётом регистра, поэтому `A.txt` и `a.txt` различаются.
Правила имён конкретной файловой системы, включая зарезервированные имена
Windows и совпадения без учёта регистра, остаются у сценария подготовки файлов.
Существующий HTTP helper `sanitizeFileName` не является валидатором ZIP-путей.

`RangeError` сообщает об ограничениях обычного ZIP:

- не более 65 534 записей;
- не более 65 535 байт UTF-8 в имени;
- размер отдельного файла и всего архива меньше 4 294 967 295 байт;
- ZIP64 не поддерживается.

Для `store` размер архива с заголовками известен заранее. Для `deflate`
дополнительно проверяется фактический размер выходных данных с заранее
зарезервированным размером финального каталога. Это позволяет обнаружить
переполнение до выделения каталога внутри `fflate`. Эти границы формата
не гарантируют, что устройство располагает достаточной памятью.
Ошибки чтения и компрессора передаются без замены причины. При любом отказе
Promise отклоняется, частичный архив не возвращается.

## Отмена и освобождение ресурсов

```ts
const controller = new AbortController();
const pendingArchive = createZipBlob(files, {
	compression: "deflate",
	signal: controller.signal
});

// Вызывается из действия отмены или при завершении сценария.
controller.abort();

try {
	await pendingArchive;
} catch (error) {
	if (!controller.signal.aborted || error !== controller.signal.reason) throw error;
}
```

Уже отменённый signal не допускает чтение или создание компрессора. Во время работы
отмена сразу отклоняет Promise значением `signal.reason`; стандартный
`controller.abort()` даёт `DOMException` с именем `AbortError`.
Переданная пользователем причина, включая `null`, сохраняется.

Потоки компрессора отменяются, таймер уступки управления и abort listener удаляются,
ссылки модуля на исходные Blob и накопленные выходные части освобождаются,
не дожидаясь чтения. Уже начатый `Blob.arrayBuffer()` нельзя физически прервать:
его поздний результат игнорируется. Само чтение может удерживать ресурсы
текущего среза Blob до своего завершения. Последующие чтения не запускаются.
После успешного завершения поздняя отмена не меняет готовый результат.

## Память и отзывчивость

Файлы обрабатываются последовательно, чтение ограничено частями по 64 KiB.
Ссылки модуля на обработанные Blob удаляются по мере продвижения. Вызывающая
сторона самостоятельно управляет временем жизни своего исходного массива.
Для `deflate` одновременно работает один компрессор. Следующая часть читается
после завершения `writer.write`, с соблюдением backpressure нативного потока.
Приложение не накапливает очередь незавершённых записей всего файла; внутреннее
буферирование компрессора определяется реализацией браузера.

Адаптер переопределяет защищённый метод `ZipPassThrough.process` и использует
`CompressionStream("deflate-raw")`. Формат raw DEFLATE не содержит обёртку zlib
и подходит для записи ZIP с методом сжатия 8.
CRC и ZIP-метаданные остаются у `fflate`; собственной реализации формата нет.
Подробности extension point: [ZipPassThrough](https://github.com/101arrowz/fflate/blob/v0.8.3/docs/classes/ZipPassThrough.md),
[Compression Standard](https://compression.spec.whatwg.org/).

CRC и сборка ZIP выполняются на основном потоке. Между частями предусмотрена
уступка event loop при исчерпании рабочего интервала 8 ms. Это не жёсткая
гарантия времени кадра: чтение, отдельный расчёт CRC и создание итогового Blob
могут занять больше времени на конкретном устройстве. Асинхронный интерфейс
CompressionStream не является гарантией отдельного OS-потока сжатия.

Выходные части накапливаются до создания итогового Blob. Такой контракт
требует места под весь архив и возможные копии браузера, даже при потоковом
чтении входа. Для многогигабайтных выгрузок нужен отдельный сценарий потоковой
записи результата; этот API не обещает постоянного потребления памяти.
